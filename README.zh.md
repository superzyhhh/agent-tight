# Agent-Tight

> 一套带预算、审计、熔断、防幻觉的编码 Agent TDD 工作流

## 📌 简介

你是否遇到这些编码 Agent 通病：

- Agent 无边界疯狂读文件，一次工单读取上百个文件，越跑越慢、上下文爆炸
- 修复评审缺陷时反复重读源码、重复校验缺陷真实性，陷入循环内耗
- TDD 测试假绿（幻觉），Agent 自己骗过自己，提交暗藏 bug
- 找不到模块接缝（seam）就无限扩大搜索范围，卡死在探索阶段
- 会话上下文被压缩丢失后，直接从头重读全部代码，无限循环

**Agent-Tight 是一套生产级闭环 Skill 规范，不是简单提示词。**

它用**预算限流、清单驱动、熔断保护、双跑陷阱门禁、全链路审计留痕**的机制，把 Agent 的自由裁量空间收束、行为可审计、可追溯，从根源解决编码 Agent 扩散、循环、幻觉三大痛点。

核心设计思想：

> 先计划、再读取；先清单、再修改；先证据、再放行；超限即停止，假设必标记。

✅ 效果变化：

- **探索阶段**：从无上限读 100+ 文件 → 单工单硬上限 15 次全文件读取 + 3 次搜索，定向读取优先
- **修复阶段**：逐个缺陷反复重读、二次评审校验 → 以 `fixes.md` 为唯一清单，禁止重复核验评审结论，片段读取优先
- **幻觉防护**：单测自判假绿 → 主用例 + 陷阱用例**双跑门禁**，退出码作为唯一判定依据，独立 Agent 盲审校验
- **卡死兜底**：找不到接缝无限搜索 → 2 轮定向探索无果则标记 `assumed` 降级假设，继续推进，评审阶段复核假设
- **上下文丢失**：重新全盘读代码 → 全阶段产物落地磁盘（`plan.md` / `notes.md` / `fixes.md`），上下文丢失时读取清单恢复状态，不重读源码

## 🚀 快速上手

### 1. 支持平台

Trae（推荐）、Cursor、Windsurf，支持任意编程语言、任意测试框架（pytest / jest / junit / go test 等）。

### 2. 安装导入

1. 下载本仓库 `skills/` 下的四个技能目录：`tdd/`、`implement/`、`code-review/`、`test-hallucination-guard/`（每个目录含 `SKILL.md` 及其附属文件）
2. 打开你的 Agent 配置面板，导入整套 Skill 包
3. 在工单 / 任务开头，启用本套工作流

> 可选：在全局配置默认开启，所有代码工单自动套用这套约束。

### 3. 首次运行最小验证工单

新建一个简单需求，例如：

> 给工具函数增加入参非空校验，补充正向、反向测试用例

提交工单，观察行为：

1. Agent 优先生成 `plan.md`，写明计划读取的文件、读取目的
2. 读取操作写入 `notes.md` 审计记录
3. 缺陷统一汇总至 `fixes.md`，再开始修复
4. 修改完成自动执行【主测试 + 陷阱测试】双跑门禁
5. 全部通过后，`code-review` 审计整个流程是否超预算、是否违规

### 4. 目录产物说明（Agent 自动生成）

```
.scratch/<ticket-id>/
├── plan.md      # 探索计划：读取目标、依赖、接缝猜想
├── notes.md     # 审计台账：每一次文件读取、搜索记录，超预算说明
├── fixes.md     # 修复清单：缺陷、文件、行号、修改方案（修复阶段唯一信源）
├── main.xml     # 主测试报告
├── trap.xml     # 陷阱（负向）测试报告
└── runs.txt     # 测试执行日志
```

## ⚙️ 参数调优说明

> 所有阈值为**生产经验默认值**，你可以根据项目规模、代码体量自行修改，在对应 skill 文件头部调整。

| 参数 | 默认值 | 含义 | 调优建议 |
| --- | --- | --- | --- |
| 单工单最大全量读取 | 15 | 整个工单探索阶段最多允许 15 次完整文件读取，超出必须记录理由，否则评审打回 | 小型项目 / 微服务：下调至 8~10；大型单体复杂项目：上调至 20（不建议超过 25） |
| 搜索次数上限 | 3 | 探索阶段 grep / 代码搜索总次数上限 | 业务简单、接口清晰：2；老代码、遗留系统：4 |
| 单缺陷读取预算 | 2 | 每一个修复缺陷最多 2 次文件片段读取 | 固定不建议改动，防止单点扩散 |
| 接缝探索轮次 | 2 | 寻找 seam 接缝最多定向搜索 2 轮，找不到就降级假设标记 `assumed` | 一般不修改；框架高度耦合的老系统可改为 3 |
| 连续失败熔断阈值 | 3 | 连续 3 个缺陷修复测试失败，立即停止工单，上报人工 | 追求稳定：改为 2；想给更多重试机会：4 |
| 陷阱用例占比 | ≥30% | 负向 / 陷阱用例数量不低于总用例 30%，对抗测试幻觉 | 核心业务逻辑：提升至 40%，普通工具函数维持 30% |

### 调优原则

1. **阈值越小**，收敛越快、越省 token，但复杂需求更容易触发假设、熔断
2. **阈值越大**，Agent 探索空间更高，但更容易回到扩散、慢的老问题
3. 优先修改【全量读取上限、搜索上限】，熔断、接缝轮次尽量不动

### 豁免规则（固定，不建议修改）

仅当 diff **没有任何可执行代码变更**（仅注释、文档、README 修改），自动跳过全套双跑门禁，减少无效开销。

## 📖 核心流程简述

1. **TDD 探索阶段**：写 plan → 定向搜索 / 读取 → 记录 notes，预算封顶，2 轮找不到接缝则标记 `assumed`
2. **实现阶段**：按计划开发，补充正向、陷阱测试用例
3. **Code-Review 评审阶段**：输出结构化 `fixes.md`，同时审计探索预算、读取行为合规性
4. **修复阶段**：严格以 `fixes.md` 为清单；同文件、行号不相交缺陷可批量修改，其余串行；不重复校验缺陷真实性
5. **Guard 护栏门禁阶段**：双跑测试、`tree_hash` 校验陷阱文件、独立盲审 Agent 校验，退出码为唯一判定标准
6. **熔断触发**：达到失败阈值，停止自动修复，输出标准化报告交给人工介入

## ⚠️ 已知局限 & 风险说明

1. 默认全量门禁，小行级改动（修改常量、文案）也会执行完整双跑，开销偏高；可自行扩展轻量护栏分支（可选扩展）
2. 没有内置模型适配，不管是 GLM、DeepSeek、Qwen 等私有 API，只要支持工具调用 + SSE 流式推理均可使用
3. 本 Skill 是**行为约束规范**，不能消除大模型本身底层幻觉，只能通过流程、证据、校验大幅压低幻觉概率
4. 假设标记 `assumed` 的接缝，需要人工在评审阶段重点复核，不能完全交给 Agent

## 🧩 来源与原创声明

本套 Skill 由两类来源组成，使用与二次分发时请保留本声明：

| Skill 文件 | 来源 | 性质 |
| --- | --- | --- |
| `test-hallucination-guard` | **本项目原创** | 原创作品，核心机制为双跑门禁、退出码取证、`tree_hash` 陷阱完整性校验、独立盲审 Agent、负例配额与 trap 隔离协议 |
| `tdd` | Matt Pocock | 来自 Matt Pocock 的 skills 集合，**已做适应性调整** |
| `implement` | Matt Pocock | 来自 Matt Pocock 的 skills 集合，**已做适应性调整** |
| `code-review` | Matt Pocock | 来自 Matt Pocock 的 skills 集合，**已做适应性调整** |

**`test-hallucination-guard` 为原创**：它把"测试全绿"这句声明变成可取证、可审计的门禁判断，是本套工作流的差异化核心，也是三份上游 Skill 之外的唯一新增护栏。

`tdd`、`implement`、`code-review` 三份源自 Matt Pocock，在原始版本基础上做了以下适配改动：

- **探索预算**：新增 `plan.md` 计划前置与 `notes.md` 读取审计台账，设定全量读取与搜索硬上限
- **修复阶段**：新增 `fixes.md` 清单化修复循环，逐缺陷读取预算、disjoint hunks 批量标准与熔断规则
- **门禁衔接**：补齐与 `test-hallucination-guard` 的调用点、产物式完成标准、评审裁决行与豁免声明
- **评审核对**：`code-review` 增加对探索预算、修复预算、读取行为合规性的审计处置规则
- **接缝降级**：找不到接缝时标记 `assumed` 并继续推进，交由人工在评审阶段复核
